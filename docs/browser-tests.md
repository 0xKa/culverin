# Extension browser checks

`bun run test:browser` builds two local artifacts and runs `tests/browser-smoke.ts`. Product scenarios load the production build in `extension/dist`; diagnostic scenarios load `.bun/test-extension`, built explicitly by `bun run build:test-extension`. Each suite uses a fresh browser profile, prints its artifact path and scenario names, and stops with the failed scenario name. Shared support owns exact artifact and permission/CSP checks, profile setup and cleanup, routed GitHub fixtures, and action-popup controls. `CHROME_BIN` selects a Chromium or Chrome for Testing executable; Google Chrome ignores `--load-extension`.

Product scenarios execute sequentially. Setup installs deterministic routes and discovers the extension. Diagnostic denial checks prove that fixture, counter, bootstrap, and feasibility requests cannot create offscreen work or make network requests in the production extension. Page/popup lifetime checks establish navigation, hydration, cancellation, and no-request-on-open behavior. Result checks establish displayed totals, disclosures, cache reuse, and reanalysis retention. Ignore/access checks exercise rules and trusted sender boundaries. Partial-result checks cover oversized files and compatibility with cached count-only results. Acquisition checks cover chunking, worker interruption, viewer detach, and recovery. Page-counting checks cover explicit and opt-in counting, rate limits, and accessibility. GitHub/History checks cover device flow, token staging, account boundaries, scoped clearing, and remembered sections.

Repo About section visibility checks exercise all three choices through the built settings page, switch page privacy without acquisition, keep the popup available while the row is hidden, and verify that the private-repository choice is saved across settings reloads. Unit checks cover unknown page visibility, preserved hidden progress/results, and stale responses during same-document navigation.

Accent icon checks select every preset and verify that the background successfully calls Chrome's real toolbar icon API with the matching packaged images. They check that the popup and settings marks follow the same accent, light and dark themes, and high contrast, use the system text color in forced-color mode, restore the saved accent after reloading settings, and make no acquisition request. They also check that older Indigo and Violet preferences select Purple, use its current toolbar images, and normalize the locally remembered value after reloading. Unit checks cover restoring the toolbar preference on worker start, browser startup, and installation, stale preference reads, rapid changes, and failed icon updates; asset checks verify the white artwork and contrast of every packaged size. The package checks allow exactly the original blue icons and the five generated accent variants.

The diagnostic suite composes the current production background and archive core with entrypoints under `tests/extension/`. It exercises direct archive/counter fixtures, leases, synthetic blocking, WASM traps, fresh memory, and restart reconciliation. Its synthetic worker delay is injected into the shared archive worker implementation; the release worker receives no delay hook. Diagnostic handlers and the alternate feasibility worker are absent from the production bundle. There is no runtime setting that enables them in a release.

Mutable GitHub fixture data is a typed `FixtureState` shared by reference. Scenario inputs and returned values are typed; browser-evaluated functions keep serialized arguments explicit. The restart scenario shares its mutable version ID through an object so later scenarios see service-worker updates. Request-count assertions retain the original sequence; scenarios must not run concurrently against the same profile.

`bun run test:package` loads the extracted production ZIP through `--product-only`; it does not load the diagnostic artifact. `CULVERIN_EXTENSION_DIR` selects the production artifact for product scenarios. `--diagnostic-only` runs the separate diagnostic suite without rebuilding. The normal browser command and `verify` retain both suites.

All network acquisition is routed by default. `CULVERIN_LIVE_PUBLIC=1` explicitly enables the additional public-GitHub scenario. Real credentials are never required. Profile cleanup runs after scenario failure, and browser startup failure also removes its temporary profile. Screenshots generated by the suite remain under ignored local output paths.

`bun run screenshots` builds the extension and captures the popup, the settings sections, and the repository page row against the same routed fixtures, in light and dark mode plus forced colors for a full result. Pass a label to keep sets apart, such as `bun run screenshots before`; images go to the ignored `.bun/screenshots/<label>/` directory. It is a review aid for visual changes and makes no assertions.

## Manual checks

Run `bun run build`, then load or reload `extension/dist` as an unpacked extension at `chrome://extensions`, and refresh GitHub tabs and the settings page so they use the new build. Acquisition requests originate in the service worker, so inspect them from Culverin's service-worker DevTools rather than the GitHub tab's. Its Network panel can throttle or go offline to make loaders, cancellation, retries, and failures observable, and should show that public `api.github.com` and `codeload.github.com` requests carry no Authorization or Cookie headers. Emulate `prefers-reduced-motion: reduce` in DevTools to confirm that loaders and badge marks stop animating. Restore normal networking when finished.

Choose Teal or Purple in Appearance while the popup is open. Confirm that both header marks change immediately and that the pinned toolbar icon keeps its white symbol on the chosen dark background. Restart Chrome and confirm that the toolbar restores that choice without opening settings. Selecting Blue restores the original toolbar icon; the installation artwork and GitHub page mark keep their existing colors.
