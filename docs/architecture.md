# Architecture decisions

Culverin is a browser-local Chrome Manifest V3 extension. GitHub supplies repository metadata and source archives; the extension analyzes source in the browser. There is no Culverin server, native companion, or telemetry service.

## Extension boundaries

- Repository page's Repo About section visibility chooses Everywhere, the default, Public only, which hides the rows on private repositories, or Hidden; screen readers announce them as Show everywhere, Hide on private repositories, and Hide everywhere. Its description updates to explain the selected choice. It controls every Culverin About row, including Analyze, progress, access notices, and results, without changing the When to count setting or toolbar popup. The independent sync preference is `culverin.aboutVisibility`, stored only when non-default. The content script waits for its trusted display reply before showing the row, reads GitHub's `octolytics-dimension-repository_public` marker only when the repository-name marker matches the current page, and can also learn visibility from a normal lookup or analysis reply when the marker is absent. Unknown page visibility remains visible. Private repositories are hidden regardless of whether Culverin has access to them. Display replies expose only the visibility preference alongside the existing layout and formatting choices. Focus and visibility recovery refresh these local choices without a GitHub request, and hidden rows retain their current progress or result for later display. The script observes in-place privacy-marker updates as well as navigation and sidebar changes.
- The TypeScript service worker owns GitHub requests, credentials, job coordination, and cancellation. Packaged settings-page controls, the extension popup, and GitHub content-script controls have separate sender gates. Public page requests must come from a top-level GitHub document and match the tab's current repository overview URL, which can change within the same document. Popup requests and replies travel on a long-lived port that the service worker accepts only from the packaged `popup.html`, whether Chrome shows it as the toolbar popup or in a tab. Chrome omits frame and document IDs for the toolbar popup, so the port itself identifies the popup; the popup reconnects on its next request after a service-worker restart. Lookup, status, and Analyze requests are checked against the active GitHub repository tab; a cancel request only needs to name that tab's running popup analysis, so switching tabs neither cancels the analysis nor prevents a later cancel. When Chrome reports no active tab in its last-focused window while the toolbar popup is focused, only that toolbar sender may fall back to the active tab in the requested repository tab's browser window; another focused tab, an inactive requested tab, and popup documents opened in tabs retain the original rejection checks. Only the settings page can connect, disconnect, or clear private results. The worker binds each subscription to its tab or extension document, navigation, and request IDs.
- The GitHub content script adds one Shadow DOM element to the About list on supported repository overviews, including URLs with query strings such as `?tab=readme-ov-file` and fragments. A `/tree/<ref>` URL, such as `/tree/main` or `/tree/feature`, is the overview of that branch, tag, or commit; GitHub shows its About sidebar there but not on folder, file, or other repository pages, so the row appears on a `/tree/<ref>` page only once the About forks row is visible, and the whole rest of the path is the ref, because Git does not allow both `a` and `a/b` as branches. The service worker reads that ref from the tab URL, never from the content script, and a ref equal to the default branch counts as the default branch, so `/tree/main` and the repository root share one result. On the repository root, the script runs at `document_start` and starts the lookup as soon as GitHub's repository marker in the document head names the current repository, so metadata resolution overlaps page loading; the About forks row is a fallback trigger for same-document navigation. Branch overviews wait for the About forks row instead, so folder pages, which share the `/tree` prefix, never start lookups. A page adapter anchors the row after the visible About forks row, and waits until GitHub's enclosing React app is marked loaded so the row never interferes with hydration; when the About sidebar is hidden, as in narrow layouts, no row is shown. The element uses GitHub's color variables and GitHub's 8 pixel spacing between About items, so it matches the neighboring repository stats. Until a result is known it shows one row, Analyze with Culverin before a count and progress or a notice otherwise, with the monochrome Culverin mark, fitted to device pixels as described under the extension icons below and drawn in `currentColor`; while a count runs, the spinner replaces the icon. With a result it shows up to three rows, by default in this order: the compact code-line total, the number of regular files at the analyzed commit, and their total size, with the Lucide `code`, `files`, and `database` icons drawn in `currentColor`; each row's tooltip gives the exact value, and the size row's tooltip also says that Git history is not included. The file count and size cover every regular file in the snapshot, as `coverage.regularFiles` and `coverage.totalBytes` define in [result semantics](result-semantics.md), so they do not depend on ignore rules. Query and fragment changes and GitHub sidebar re-renders keep the same view and move the row back into place. A bounded URL check detects same-document route changes even without DOM mutations; DOM mutations and window resizing remain recovery signals. When the local cache holds no result for the page's owner and name under the current rules, or on another branch's overview no result looked up under that branch, a page lookup makes no GitHub request and the row offers Analyze with Culverin; if an earlier request hit the rate limit and its retry time has not passed, the row shows the rate-limit notice instead. Otherwise the lookup resolves metadata and may show a compatible cached total without downloading an archive, or offers to count when the commit or rules no longer match. The When to count setting can instead count when the page opens: the lookup then always resolves metadata, and on a cache miss the service worker tells the content script to start the same analysis a click would. It does so at most once per repository, commit, and rules per browser session, tracked in session storage and reset by clearing public or all saved results, so a failed or canceled count is not repeated on every visit. A trusted click on that row, like the popup's Analyze action, permits a SHA-specific source snapshot download. While a page analysis runs, the row shows its progress and a trusted click opens the popup, which attaches to that same job through the service worker, shows its progress and result, and offers Cancel; cancelling there stops the page's count and returns the row to Analyze with Culverin. Downloading, unpacking, and counting overlap, so progress only moves forward through those phases: once counting has started, a later download update does not bring back the downloading label. A job reports the downloading phase as soon as it starts running, and keeps reporting how many bytes it has downloaded after counting starts, with the number of regular files the worker has read, which each chunk acknowledgement carries, at most every 250 milliseconds; the page row receives only phase changes, and the downloading phase only once the first bytes arrive. A trusted click on a complete total asks the service worker to open the toolbar popup for the active tab with `chrome.action.openPopup`, which needs no extra permission and is why Chrome 127 is the minimum supported version. A failed analysis offers a retry, a rate limit shows a notice until its retry time, and size limits and unsupported snapshots show a notice without a total. A count that started when the page opened and reached the 256 MiB automatic download limit, or its unpacked limit, instead shows Too large to count automatically, with a tooltip offering to count up to the user's Large repositories limit when that is higher; a trusted click starts an ordinary count with that limit, and the popup shows the same message with its Analyze action. The automatic attempt is not repeated in the same browser session. When source files were too large to count, the code-line total ends with `+` and its tooltip says how many files it leaves out; the popup shows the same note above the full result. A lookup that resolves an empty repository hides the row. When GitHub reports a repository as missing, which is how a private repository looks without access, the row says that it may be private and a trusted click asks the service worker to open the GitHub section of the settings page in a new tab; with a connection that cannot read the repository, the row reads Culverin can't access this repo, with the same click, and the popup badge reads Not shared instead of No access. The toolbar popup contains the full analysis UI; its explicit Analyze action permits a SHA-specific source snapshot download. Opening the popup makes no GitHub request: its lookup reads only resolutions kept from the last 20 minutes. Resolutions are kept per repository and ref, and each is also kept under the name of the ref it resolved to, so the repository root, `/tree/main`, and files on `main` share one, as do a branch's overview and its folders, unless another branch or tag is named below that ref, such as a branch `release/v2` beside a tag `release`. Without one, the popup shows the repository name and Analyze, and Analyze resolves metadata before counting. Once a result is shown, the button reads Reanalyze; Reanalyze resolves metadata again even within the 20-minute window, shows the cached result when the commit and rules are unchanged, and otherwise downloads and counts the new commit. The popup's totals show code lines and, smaller and right-aligned on the same row, the number of regular files at the analyzed commit, with a tooltip giving how many of them were counted as code or text and how many as other files, wrapping below only when both numbers do not fit; code-line totals of a million or more use a slightly smaller size so typical large repositories still fit on one row. Below them are text lines, the prose lines of documentation formats defined in [result semantics](result-semantics.md), physical lines, comments, and blanks. Its details list files that are not recognized as a language by extension, with their line counts, in an Other files section that does not add to code or text lines. The GitHub settings show how many core API requests remain out of the hourly limit, or the connected account's limit once a connection is used, with its reset time, updating while open. Their Show API requests in the popup option, off by default, adds the same count to the popup header, such as `API 57/60`; it is stored as `culverin.popupApiLimit` only when on, remembered locally for startup, and applied as `data-api-limit="shown"` on the popup's root element, so an open popup follows the change. The meter is display only: the count is recorded either way, and hiding it makes no request. Beside each count, a small bar fills with the share left and turns amber once half the limit is used and red at 80%. The service worker reads the count from the `x-ratelimit-*` headers of its lookup responses, including rate-limited ones, so showing it costs no extra request. When the count is unknown, the GitHub requests panel in the GitHub settings offers Check now, and once known a Refresh icon button; either asks the service worker for the core limit. Without a connection, it reads GitHub's `/rate_limit` endpoint, which GitHub does not count against the limit. With a connection, it reads the `x-ratelimit-*` headers of an authenticated `/user` request, which uses one request, because GitHub's `/rate_limit` reports an unused window for connected tokens that disagrees with the headers of their other requests. A rejected token expires the connection as other requests do, and a reply that arrives after the connection changed is discarded. The service worker keeps the lowest count seen for the current reset window, replaces a stored window with any response whose reset time is still ahead even when it is earlier than the stored one, so a contradicting count cannot hide later requests, tags counts from authenticated requests, and does not let an anonymous fallback request replace a connected account's count, and the popup shows the full limit once the reset time passes. Archive downloads are not counted, because GitHub tracks them separately from the core limit. A core API rate limit blocks new GitHub requests for the same connection until the response's `Retry-After` time, or until the reset time when the core limit is used up, and otherwise for one minute. When `codeload.github.com` throttles an archive download, the failure says GitHub is busy preparing the source snapshot and offers a retry without blocking other repositories, because that throttle is not the core API limit. A result, including a cached one, shows one Size: the total size of the regular files at the analyzed commit, as checked out, with a tooltip saying that it excludes Git history, so a cloned folder with its `.git` folder is larger. No size is shown before a result. When GitHub's metadata reports a repository size, Analysis details add an estimated clone size: the files' size plus that reported size, which covers compressed Git history and is only updated occasionally by GitHub, so the tooltip says a real clone may differ. The estimate needs no extra request because the size comes with the metadata Culverin already resolves. While a count runs, the popup shows a live elapsed time such as `1:42` under its loader, counted from when the job started rather than when the popup opened, and Waiting for another count while the job is queued; the timer is hidden from assistive technology and ticks once a second. Below the timer, the popup shows how many regular files the counter has read so far, such as 12,480 files read, in the popup's number format and also hidden from assistive technology; like the result's file count, it includes code, text, other, and skipped files, and because downloading and counting advance together it also tracks the download. Until GitHub sends the first byte, the status reads Waiting for GitHub to send the source snapshot…; once counting starts it reads Downloading and counting source files locally…, because the download advances only as fast as the counter accepts data. The coordinator records when each job starts running and sends that time with progress and with `analysis.status`, so a reopened popup shows the true elapsed time. When a count finishes, the coordinator adds its duration to the output; the service worker keeps it as an optional `durationMs` beside the saved result, without changing the result schema, and returns it with completed analyses and cache hits. The archive bridge also measures how long it waited for GitHub, for the archive response and each read, and how long it waited for the counter to accept each chunk and finish; because the counter accepts data only as fast as it counts, the two show which side limited the count. The cache keeps them as optional `githubWaitMs` and `counterWaitMs` beside `durationMs` only when both are whole milliseconds that together do not exceed the duration, and ignores an invalid stored value without dropping the result. The service worker returns them with completed analyses and cache hits, and the popup's Analysis details then read, for example, Waited 38s for GitHub and 4.1s for the counter; the line stays with its displayed result during reanalysis until a new result replaces it, and saved results without wait times show none. Under the status badge, the popup shows Counted in 2m 04s for a new result, Took 2m 04s when counted for a saved result that has a duration, and Stopped after 3m 10s when a running count fails or is canceled; saved results from earlier versions show no duration. Durations under a second show milliseconds, such as 412ms, under 10 seconds one decimal, such as 4.2s, and under a minute whole seconds, such as 42s. The text is announced once through the popup's status live region. The page row is unchanged. A popup analysis belongs to its repository tab rather than to the popup document: closing the popup does not cancel it, and a reopened popup on the same tab resumes its progress and result through `analysis.status`, including after a cache hit, so a reopened popup during Reanalyze keeps the cached result displayed and offers Cancel until the new result arrives. The popup recognizes the repository on any of its pages. On `/tree`, `/blob`, `/blame`, and `/commits` pages it analyzes the branch, tag, or commit at the start of the path, choosing the longest leading part of the path, among at most five, that names a branch or tag, as [result semantics](result-semantics.md) describes, even when the path starts with the default branch followed by `/`. Folder and file paths reuse a cached ref resolution only after ref discovery confirms there are no nested branch or tag names; a cached root result alone does not establish this. An unresolved popup path offers Analyze without making network requests. On `/commit/<sha>` and `/releases/tag/<tag>` it analyzes that commit or tag; issues, pull requests, release lists, graphs, and other pages analyze the default branch. Its Analysis details name what was counted, such as `main, commit 1a2b3c4d5e6f`; a branch or tag other than the default branch is highlighted with a tooltip that names it and the default branch, and a commit page reads `commit 1a2b3c4d5e6f` highlighted the same way. In the popup and Saved results, a ref name too long for its line ends in an ellipsis instead of wrapping, and its tooltip gives the full name; top-level GitHub paths that cannot be account names, such as `settings`, `orgs`, `marketplace`, or `topics`, are not read as repositories. Moving between pages of the same repository keeps the analysis; navigating that tab to another repository or away from GitHub repositories, or closing it, cancels the analysis. After a result, the service worker sends the code-line total, the number of files too large to count, the number of regular files, and their total size to the matching repository page, with the counted ref and default branch, and the page shows them only when they match its own ref, so a count for one branch never appears on another branch's row. While a popup analysis runs, the service worker also sends each new phase to the tab, with the page URL, without query or fragment, at the time the analysis started. The row shows that progress only while it is still on that URL, is not running its own analysis, and has no result displayed, so a displayed result stays in place during a popup Reanalyze until the new one arrives. If the analysis fails, is canceled, or finishes under different rules, the row returns to what it showed before. The content script can read a compatible public or private aggregate cache result or its own page analysis result, but renders only the code-line total, the file count, and the total size, and never receives credentials, archive URLs, or source files. The packaged settings page exposes the ignore rules in its Ignored files section, controls to clear public, private, or all saved results and lists of saved public and private results in its Saved results section, where each result can be shown in a read-only, popup-sized dialog that reuses the popup's result components, or deleted, the GitHub connection, the GitHub request count, and common questions about GitHub's request limit in its GitHub section, in its When to count section whether counting starts on an explicit action, the default, or when a repository page opens, in its Repository page section, second in the sidebar below Appearance, which result rows the About list shows and in what order, with a live preview, and in its Appearance section, first in the sidebar, whether the popup and settings follow the system color scheme, the default, or always use light or dark. Its independent High contrast option is off by default and strengthens text, borders, controls, status colors, and focus rings in the popup, settings, and saved-result dialogs. Accent color chooses Blue, the default, Copper, Purple, Pink, Teal, or Slate for links, highlights, buttons, focus rings, and single-color language bars in the popup, settings, and saved-result dialogs; the choices are square color swatches after Theme, named in a tooltip and to screen readers and shown as text in forced-color mode, and retain the default accent's lightness levels, and adjust its hue and chroma. Contrast checks cover every preset in light, dark, and high contrast modes. Non-default choices are applied as `data-accent` on the root element. Older saved Indigo and Violet values are read as Purple in both sync storage and locally remembered preferences; new choices are saved with the current preset names. Language colors chooses By language, the default, which colors code and text rows in popup results, saved-result dialogs, and the appearance preview with a consistent color per language from GitHub Linguist, or Single color, which keeps the single accent, and Language markers chooses a square, the default, a circle, or no marker beside each colored language name; [language colors](language-colors.md) describes its sources, rendering, and contrast. Numbers and Size units choose full counts (the default) or locale-aware abbreviations and binary KiB/MiB (the default) or decimal KB/MB. They apply to popup results, saved-result dialogs, the Saved results list and usage figures, and the appearance preview. Exact counts remain in accessible language-row labels and in hover/focus tooltips for abbreviated values; size tooltips include exact bytes. Open result views follow trusted sync-storage changes without a lookup or analysis, retaining their disclosure state and displayed result during reanalysis. API budgets, coverage notes, and archive limits retain exact counts and fixed limit units. Repository page has independent Numbers and Size units choices, defaulting to abbreviated counts and binary KiB/MiB; its preview responds to both. Page counts retain GitHub-style lowercase k abbreviations, while Full uses exact English-grouped counts. Both modes retain exact native tooltips and partial-result markers. Page formatting preferences use separate trusted sync-storage keys from the popup and settings preferences. Both UI entrypoints apply locally remembered contrast, accent color, and language colors at startup and follow trusted sync-storage changes; GitHub repository pages retain their GitHub appearance. Below the appearance choices, a popup preview uses fixed, clearly labeled sample data and the shared popup totals, size, and language-breakdown components. It follows the same theme, contrast, number format, and size units as the settings page, including live system color-scheme changes, and reads no saved results or repository data. Its element IDs are prefixed so the sample can coexist with a saved-result dialog. Deleting one listed result asks the service worker, which removes that single entry within the cache's serialized writes and leaves resolutions and other results in place. The Counting choice, the About list layout, the theme, high contrast, accent color, language colors and markers, the popup API meter, and the independent popup and page number formats and size units are stored in trusted-only `chrome.storage.sync` only when they differ from the default, through one shared preference definition that gives each setting its key, default, and validation. The layout keeps every item's position, including hidden ones, so showing an item again restores its place; at least one item stays shown, and unknown items are dropped when it is read, so items added later appear in their default place. The saved results list reads the public cache from trusted-only `chrome.storage.local`, keeps only entries that pass the cache's own validation, and shows each repository, with the branch, tag, or commit it was last looked up under on its own line below the name when that is not the default branch, highlighted and linked to its `/tree` page, then the commit, code lines, files, main language, whether custom ignore rules applied, and when it was counted and last viewed, with the storage used against the cache limits. A cache hit records its view time at most once an hour, unless the repository's name, branch, or other metadata changed, so revisiting a repository does not rewrite the saved results; it makes no GitHub request and updates when the cache changes. Its About section shows the extension version from the manifest, the Tokei and rules versions, the Chrome major version, and the extension ID, with links to the repository, changelog, privacy policy, issues, license, and the packaged third-party notices; Copy details writes those values to the clipboard only when the user selects it. A sidebar groups the sections under Display, with Appearance and Repository page, Counting, with When to count, Ignored files, and Large repositories, and Account & data, with GitHub and Saved results, followed by About below a divider; each entry has a Lucide icon, and on narrow windows the group names and divider are hidden and the entries wrap in one row. It switches between sections through the URL fragment, such as `settings.html#storage`. Without a known fragment, the page opens the section last shown, which it keeps in the extension origin's `localStorage`, or else the first sidebar section; the popup's Ignored files Edit action selects that section before opening the page. The service worker ignores the fragment when it checks that a request comes from the settings page. Ignored files turns built-in exclusion groups on or off and adds custom exclusions; the settings page writes them to `chrome.storage.sync`, restricted to trusted extension contexts. The service worker reads the current settings for each lookup and analysis, uses their rules hash for cache and job identity, and passes the rules to the analysis worker; results counted under other settings remain cached but are not shown. When the settings differ from the defaults, the popup summarizes them with a link to the settings page, and a lookup that finds only results counted under other settings says that the rules changed. The content script never reads settings storage. It asks the service worker for the About items to show with a `display.get` request when a view starts and again whenever its tab becomes visible, so layout and formatting changes apply when the user returns to the repository page; the reply contains only the ordered item names and validated count-format and size-unit enums. It redraws an existing result without acquisition and ignores superseded display replies. It compares a result's rules hash with the default hash only to add an ignore rules note to the row's tooltip.
- Public page messages use a closed version-1 request and reply protocol. A lookup returns a cache hit or miss after a compatible resolution confirms public visibility; a page lookup without a cached result returns `repository.not_cached` without resolving, and a cache miss may carry `autoCount` when the When to count setting counts on page open. A popup lookup never resolves: it returns a cache hit or miss from a resolution kept in the last 20 minutes, or `repository.not_cached` without one. Only popup analysis requests may carry `reanalyze: true`, which bypasses the kept resolution. A page may also ask the service worker to open the toolbar popup; the popup port rejects that request. Resolution metadata, including its timestamp and GitHub's reported repository size, lives outside the deterministic result. Both worker and page validate result identity against the resolution before display. One archive analysis runs at a time; identical explicit requests share it, while distinct requests wait in a bounded queue. Page and popup replies may carry public or private resolutions; the aggregate result is the same either way.
- A GitHub connection is optional. Without one, every request is anonymous. The settings page offers two equal ways to connect, shown side by side. One is the device flow of the Culverin GitHub App, whose only repository permissions are Contents and Metadata, both read-only: the service worker requests a device code from `github.com/login/device/code` with the app's public client ID, the settings page shows the user code with a copy icon button, which reports the copy result beside it, and a link to `https://github.com/login/device`, and the page asks the service worker to poll `github.com/login/oauth/access_token` at the interval GitHub sets until the user approves, declines, or the code expires. No client secret exists in the extension, and the token form stays disabled while a code is waiting for approval. The other is a personal access token, preferably fine-grained with read-only Contents access: the settings page writes it with a random submission ID to trusted-only session storage, where it waits at most 60 seconds, and the service worker reads and deletes it, checks it with `GET /user`, and saves it. Both flows record the GitHub login for display. The connection lives in trusted-only `chrome.storage.local` as a single record with a generation ID, so it survives browser restarts without asking again. App tokens expire after 8 hours; the service worker refreshes them with the refresh token, which GitHub allows without a client secret for device-flow tokens, one refresh at a time and at most 5 minutes before expiry, and keeps the old token until it expires if GitHub is unreachable. A refresh that GitHub rejects, or a 401 from any request, marks the connection expired: the tokens are deleted, the login is kept to explain what happened, and requests fall back to anonymous. Connecting, disconnecting, expiry, and clearing private or all results each start a new generation; the service worker aborts jobs from the old generation, drops kept resolutions and the stored rate limit, and a connection attempt that started under an older generation is discarded. Private lookups and analyses already in progress check the generation again before showing a saved private result, starting a job, or keeping a finished result, and end as interrupted if it changed. Disconnecting, and connecting a different GitHub account, also delete private results. Tokens stay in the service worker and settings page: content scripts, the popup, the offscreen document, and analysis workers never receive them, and archive redirects carry GitHub's own signed URLs rather than the token.
- With a connection, page and popup lookups resolve metadata with the token, so they count against the account's limit of 5,000 requests per hour. Kept resolutions are keyed by generation. If the token cannot see a repository, the service worker retries once anonymously so public repositories keep working even where the app is not installed. A private resolution selects the private result cache and a job whose identity includes the generation, and the archive is downloaded with the token; public archives are downloaded anonymously. A private resolution also removes any public result and public resolution for that repository. When a connected lookup reports a repository as missing, private results saved under that name are deleted. Rate-limit waits are tracked separately for anonymous requests and for each generation.
- An offscreen document hosts a dedicated, terminable analysis worker. The service worker transfers bounded archive chunks to it with acknowledgments. Control commands (start, renew, finish, cancel) travel over `chrome.runtime` messaging. Chunks of at most 1 MiB travel as transferred `ArrayBuffer`s through the Clients API: the service worker finds the offscreen document with `clients.matchAll` and posts each chunk to it, and the host replies through the message source. The host accepts a chunk only from the extension's own service worker script, for the active job, and in sequence; the service worker accepts a reply only from the offscreen document. One chunk is in flight at a time. If the offscreen document is not found as a client, chunks fall back to base64 strings over `chrome.runtime`. No chunk message carries a token or signed URL. The worker decompresses gzip, validates tar entries, applies file limits, and calls a fresh Rust/WASM counter for each job. The service worker receives the aggregate result and transport diagnostics, not source files.
- The Rust counter uses Tokei and exposes the same counting boundary to native tests and browser WASM. The result contract is [`schemas/analysis-result-v2.schema.json`](../schemas/analysis-result-v2.schema.json). Counting rules, coverage, archive handling, and resource limits are specified in [result semantics](result-semantics.md). An interrupted, canceled, malformed, or resource-limited job returns a failure rather than a complete result.

The popup and settings apply the chosen theme as a `data-theme` attribute on the root element. Before their first render they read it from a copy in the extension origin's `localStorage`, so a saved theme shows without a flash of the other one, then confirm it from sync storage and follow later changes, so open pages switch at once. The dark palette and the `dark` variant apply under that attribute, or with the System theme under `prefers-color-scheme: dark`, and `color-scheme` follows a chosen theme so native controls match. The GitHub page row keeps GitHub's colors, so it follows the theme chosen on GitHub instead. The popup and settings share a thin custom scrollbar: a square 4-pixel thumb in the border color over a transparent track, darker on hover and while dragged, and drawn in the system text color in forced-color mode. Slow actions in the Preact popup and settings share a packaged CSS dot-grid loader, and the content script's Shadow DOM uses a small CSS spinner. For both an initial analysis and Reanalyze, the popup hides the analysis button and shows the loader centered in its place with a small Cancel analysis button below it. Reanalyze keeps the existing totals, sizes, commit, and details displayed until a replacement result is ready, preserving the details disclosure state; unchanged commits, errors, and cancellation retain the current result. Its status badge starts at Checking and advances through analysis phases if needed; the repository row on GitHub replaces its icon with the spinner only while analysis is running. Both retain their cancellation controls. GitHub settings show a small loader only while requesting a connection code or validating a token, with disabled controls and action-specific button text. The GitHub requests Refresh icon button shows a small loader in place of its icon while it checks, and is disabled until the check ends. While the GitHub code waits for approval, a small loader beside the waiting message shows that the page is still checking; when the settings tab becomes visible or focused again, it checks at the earliest time GitHub's polling interval allows instead of waiting for a timer that Chrome may have delayed in the background. The loader and spinner are hidden from assistive technology, which receives the existing status text, respect reduced motion, and follow the surrounding text color in light, dark, and forced-color modes. The popup shows no status text under the repository name. A square status badge sits to the right of the name, or of a No repository placeholder on other pages, with a short label such as Not counted, Checking, Downloading, Unpacking, Counting, Fresh, Up to date, Cached, Partial, Rules changed, Rate limited, or Failed, and a small mark: a dashed ring while waiting, a turning arc while working, a drawn check after counting, a filled ring for a cached result, and a drawn cross after a failure or cancellation. Its tone is neutral, accent, green, amber, or red. Hovering or focusing the badge shows the full status message in a tooltip, and a visually hidden polite live region announces the same message and describes the badge. Every other tooltip in the popup and settings uses the same styled tooltip instead of the browser's native one: it opens on hover or keyboard focus, so text that has one is focusable, and its text is also the element's accessible description, while icon buttons keep their label as the accessible name. The GitHub page rows keep native tooltips to match GitHub's own interface. Only two failures add visible text, below the analysis button: a rate limit shows when Analyze becomes available again, and a throttled source snapshot asks to try again in a minute. The badge mark animations stop with reduced motion. Settings that save as soon as they change, and the Ignored files Save and Reset to defaults actions, confirm each save with a small indicator beside the setting's name, at the top right of its panel for the Repository page About list and the Ignored files built-in rules, or beside the Save button for ignore rules. The Appearance options and the Repository page visibility, number, and size choices are compact rows, with the name and a one-line hint on the left and the choices on the right as a radio group; the chosen value is framed by the same corner ticks as the selected sidebar entry, hovering a choice shows them too, counts and size units are shown as monospace examples such as 12,480 and KiB, and High contrast is an Off and On choice. When to count stacks its two choices under its name with their full descriptions, framing the chosen one the same way. A setting that differs from its default shows a small reset icon button beside its name, named for the default it restores, such as Reset to System, and described by the setting's name; the Repository page About list has one beside its heading that restores every item in the default order. The choices themselves are not marked as the default. Resetting saves exactly as choosing the default does, so the stored key is removed, then the button disappears and keyboard focus moves to the restored choice, or to the first About list item. The button is disabled while its choices are, as for Language markers with Single color. The Ignored files built-in rules, Repository page About-list items, and Show API requests in the popup setting use the shared Checkbox component: a native checkbox with open corner ticks and an accent checkmark, keyboard focus, disabled states, and system colors in forced-color mode. Checking a built-in rule enables its exclusions; unchecking it includes those files in counting. The Saved results clear buttons and the About Copy details button show the same indicator beside the button, reading Cleared or Copied. It reuses the badge mark: the turning arc shows while the action runs, which is visible for clearing because that request goes through the service worker, then pauses at its current angle as it closes into a green ring, the check draws in, and the word appears. The same ring animation is retained through completion or failure, so completion does not reset its rotation. It replays on every action, so repeated changes each confirm, and fades after three seconds. A failure shows a red cross with its own text, such as Couldn't save. Try again., stays until the next action, and a failed setting save returns the control to the stored value. Deleting one saved result shows the same indicator beside its list's clear button, reading Deleted after the deletion is confirmed and fading after three seconds. The request is sent immediately, and its row stays visible until the saved result is removed. Keyboard focus moves to the next row's delete button, the previous one for the last row, or the list summary once the list is empty, unless focus moved elsewhere in the meantime. If the delete fails, or the result is still saved when the service worker replies, the row remains visible and the indicator beside that list's clear button shows Couldn't delete. Try again. The indicator is hidden from assistive technology; a visually hidden polite live region announces the result instead, naming the item and its new state for Repository page changes and the repository and commit for a deleted result. Typing in the ignore rules removes the rules indicator until the next save, and the explanations that used to follow an action are shown under the Counting and Culverin ignore headings and above the About details.

## Storage and packaging

The Saved results settings place each individual clear button beside its public or private results heading, with a separate Clear all results button below both lists. Clearing results preserves ignore rules, the When to count setting, and the GitHub credential. Clearing public results removes the public result cache, kept resolutions, and session automatic-count attempts; clearing private results uses the existing generation change to abort old private jobs and remove their saved results. Clearing all results combines both actions. These requests are accepted only from the packaged settings page and never start a download.

- Culverin makes anonymous GitHub requests unless the user connects GitHub. The connection record, including its tokens, is stored in trusted-only `chrome.storage.local`, and a token entered on the settings page waits in trusted-only `chrome.storage.session` for at most 60 seconds, as does the pending device code. Ignore rules are stored in trusted-only `chrome.storage.sync`, which Chrome syncs with the user's other browsers when Chrome sync is on. Public aggregate results are stored in trusted-only `chrome.storage.local`, bounded to 200 entries or 5 MiB. Private aggregate results are stored under a separate key, bounded to 100 entries or 2 MiB, and are shown only after a lookup with the current connection confirms the repository is still private and readable at the same commit. Cache identity includes repository ID, commit SHA, engine and wrapper versions, rules profile/version/hash, coverage policy, and result schema. Mutable names and branch labels remain resolution metadata. Page and popup ref resolutions, public and private, are kept in trusted-only session storage for at most 20 minutes, 100 entries, or 512 KiB, so they survive service-worker restarts; clearing the public cache or changing the connection removes them. Authenticated resolutions for the settings page stay in memory for at most 60 seconds. A confirmed public-to-private transition removes that repository's public resolutions from both. A confirmed public-to-private transition purges persistent results for that repository; unresolved visibility never authorizes a cache display. The service worker keeps only bounded subscriber interruption markers, the latest core API rate limit, and up to 200 automatic-count identities in session storage. Archives and source files are not persisted locally.
- Large repositories, in the Counting group of the settings page, sets the maximum download for counts the user starts: 256 MiB, 512 MiB (the default), 1 GiB, 2 GiB, or 4 GiB, stored as `culverin.downloadLimit` in trusted-only `chrome.storage.sync` only when it differs from the default. The service worker reads it when it accepts a click, popup, or settings request. Counts that start when a repository page opens are always limited to 256 MiB. The service worker does not take the page's word for which counts are automatic: when it answers a lookup with `autoCount`, it records a grant for that page navigation and identity, and only the next request from that navigation, within 10 seconds and for the same identity, consumes it and subscribes as automatic. Any other request from the navigation, a new navigation, or the page disconnecting drops the grant. Every job has its own download limit, the largest of its subscribers' limits, and an unpacked limit of eight times that. A click that joins a running automatic count raises both limits for the job without restarting it: the service worker checks downloaded bytes against the job's current limit, and sends the raised unpacked limit to the offscreen host, which passes it to the worker. A limit failure carries the job's limit in bytes, so its message names the limit that applied.
- The coordinator permits one active archive analysis, eight queued jobs with a 60-minute queue wait, and 32 subscriptions overall. Each subscriber is manual or automatic; a job is manual when any subscriber is, and the oldest queued manual job starts before any queued automatic-only job. When the queue is full, a manual job evicts the oldest queued automatic-only job, whose subscribers end as canceled; it never evicts the active job or a job with a manual subscriber. Active jobs have a 60-minute ceiling and record when they started, with separate network and worker inactivity watchdogs described in [result semantics](result-semantics.md). The engine owns these duration limits; popup and page viewers have no independent analysis deadline and stop watching on terminal replies, explicit cancellation, navigation, or transport interruption. A subscription belongs to one document/navigation, one repository tab for popup analyses, or the trusted settings page. Service-worker restart interrupts an in-flight page analysis and requires a new explicit Analyze action; it does not resume an archive download. An idle page retains its displayed result when its lifetime port disconnects and reconnects only before its next request, so worker suspension does not erase the count or wake the worker repeatedly. Disconnect callbacks from replaced ports cannot interrupt the current view’s requests.
- The manifest is explicit in `extension/public/manifest.json`. It declares `storage` and `offscreen` permissions; GitHub, GitHub API, and codeload host access; and a packaged-code CSP that permits local WASM. The existing `github.com` host permission and CSP entry cover the device-flow endpoints, so connecting GitHub adds no permission. The action opens a packaged popup that reads the active tab using the existing GitHub host permission; no `tabs` permission is added. Vite builds the service worker, popup, settings page, offscreen document, analysis worker, and packaged WASM asset. The popup and settings page use Preact components styled with Tailwind CSS; their stylesheet is compiled and packaged locally, and Preact is bundled in a named local chunk. The content script, service worker, offscreen document, and workers load neither Preact nor the stylesheet. Bun bundles the content script as a classic script because Chrome's manifest content-script entry cannot load Vite's split ESM chunks. Neither build path changes the manifest's permissions.
- Chrome 127 is the minimum supported version, the first that lets every extension open its popup with `chrome.action.openPopup`. Bun 1.4.2 runs the TypeScript build and checks; Cargo runs native Rust tests; direct WASM tests exercise the generated module; and Playwright smoke tests load the packaged extension in Chromium.

The project is licensed under Apache-2.0. The extension icon PNGs in `extension/public/icons/` are generated deterministically from the project-owned `assets/culverin-icon.svg` with `bun run icons:build`; `bun run icons:check` verifies the committed sizes. The artwork is drawn on a 16 by 16 grid, which the generator enforces, so the packaged 16, 32, 48, and 128 pixel icons scale it by whole pixels and keep even line widths. The popup and settings headings and the GitHub page row draw the same shape from `extension/src/ui/brand-mark.ts`, which a unit test keeps equal to the source artwork and to `assets/culverin-icon-light.svg` and `assets/culverin-icon-dark.svg`, the same symbol without a background for use on light and dark backgrounds outside the extension. Their sizes, 20, 56, and 16 CSS pixels, are rarely a whole multiple of the grid in device pixels, so the mark is fitted to the current device pixel ratio instead of scaled: it keeps its size rounded to whole device pixels, and each grid row and column gets the same number of pixels as the others of its kind, so the stem, both bars, and the three lines keep one stroke thickness, and the gaps between them stay equal at every display scale and browser zoom. The headings use it as a CSS mask, filled with the selected accent so it follows the theme and high contrast setting, and refit it when the device pixel ratio changes; in forced-color mode it uses the system text color. The Chrome toolbar keeps a white symbol on a square background and follows the selected accent through `chrome.action.setIcon`. Blue uses the original icon files; the other five backgrounds are generated from the light accent palette in `extension/src/ui/styles.css` by the same icon script. The background restores the saved choice when its worker starts, on browser startup, and on installation or update, and follows trusted sync-storage changes. Toolbar updates are serialized, keeping only the latest pending choice, and an icon update failure does not interrupt analysis. The manifest and installation icons keep the original blue artwork, and the GitHub page mark retains GitHub colors. No new permission or preference is added.

The popup and settings interface icons come from Lucide through `lucide-preact`, and the GitHub page's result rows use the same icons through the framework-free `lucide` package; only the imported icons are bundled at build time, and both packages are listed in the packaged third-party notices. Brand artwork remains project-owned.

Pure repository identity, validation, overview URL parsing, and comparison live in `extension/src/github/repository.ts`; the content adapter owns only DOM discovery and hydration. Popup and Saved results share display formatting through `extension/src/ui/format.ts`. These helpers have no browser API or DOM effects at import time.

One offscreen-document manager owns context checks, shared creation, leases for starting and active clients, and idle closing. Archive and diagnostic clients release ownership on completion, cancellation, deadline, or setup failure. A new acquisition invalidates a pending idle check; when closing has already started, setup waits and recreates the document before dispatching work. On service-worker startup, existing archive work is reconciled and interrupted before saved subscriber markers are reported; this does not create an offscreen document when none exists. The manager does not own archive deadlines, credentials, or job restart policy.

The background composition root creates resources and wires authentication, rate-limit tracking, public analysis policy, the trusted settings adapter, popup tab jobs, and page/port transport. Listener registration is explicit and idempotent. Shared request deduplication, pending cancellation, interruption markers, visibility revocation, and failure conversion preserve their existing bounds and keys. Public page/popup and trusted settings retain separate sender gates, resolution policies, reply contracts, and credential selection.

The default background entrypoint registers only production handlers, and `offscreen.html` loads the production archive router. `bun run build` emits `extension/dist` with one archive worker; packaging always reads that directory. `bun run build:test-extension` explicitly selects diagnostic entrypoints under `tests/extension/` and writes a separate ignored `.bun/test-extension` artifact. It composes the same production background, archive parser, and counter with fixture/feasibility handlers, an alternate feasibility worker, and a probe channel. No runtime switch can enable these adapters in a release. Package checks reject diagnostic markers and extra workers.

The archive worker's synthetic delay implementation lives in the diagnostic adapter and is injected into the shared worker core. The bounded `blockMs` field remains in the shared host/bridge protocol for test compatibility; production acquisition sends zero, and the production worker has no delay hook. The WASM `force_trap` export and trusted settings analysis used by the benchmark remain supported. Browser product scenarios and extracted-ZIP checks exercise the actual production artifact; a separate browser profile exercises diagnostic cancellation, leases, traps, fresh memory, and restart recovery. See [browser checks](browser-tests.md).
